## 3. 选型决定

**现在：Windows 编辑 + WSL Linux 兼容测试。** 两侧都可运行内核，优先完成真实模型工具环境的最小接入。既有 Ubuntu 与 VMware 足够，不额外安装另一套虚拟化平台。

**GUI 实验：Windows 宿主 VMware + Linux guest，网页服务单独部署。** 这是 RedTeamCUA 官方 README 支持的路径之一。WSL 不是完整桌面 benchmark 的自动替代品；Docker 也不能替代 GUI guest 的快照和桌面状态。

未来镜像建议放 `D:\CUA-Lab`，在正式下载前计算镜像、解压、快照与网页服务的总大小。建议预留至少 60–100 GiB 为项目规划估计，并非上游官方最低配置。15.7 GiB 宿主内存下只跑一个小型 GUI guest；guest 起始可试 4 vCPU、6 GiB RAM，同时限制 WSL 服务数量，依据实际监控调整。不在当前 C 盘下载完整 benchmark 镜像。

完整网页副本可能比一台 guest 更占资源；优先两个本地合成服务的小型扩展，正式复跑原 benchmark 再接现有团队服务器或单独部署所需平台。云实例需预算/账户信息后配置，不预先产生费用。

## 4. 验证结果与限度

Windows 和 WSL 各运行 **16 项单元测试，全部通过**。覆盖：跨会话来源保留、内联来源篡改、内容变化、unknown 来源、无效父节点事务、任务/资源/接收方精确绑定、拒绝动作不执行、调用 ID 重放、隔离闭包、不相关分支保留、旧动作复检、重建版本及调用祖先定位。

## 5. 下一阶段环境清单

1. 固定 AgentLAB/RedTeamCUA 上游 commit 和许可证，不把 upstream requirements 混入内核环境。
2. 为选定工具环境建立独立 `.venv-benchmark`，按其实际依赖选择 Python 版本，记录 lock 和正常任务 smoke test。
3. 真实模型接入需要 provider、精确模型 ID、API key 和试验预算；key 只写本地环境，不能进入 Git。
4. GUI guest 下载前确认磁盘路径与实际镜像总量；镜像可清理重建，但不得自动删除用户既有 VM。
5. 先证明正常任务可完成，再注入攻击和装载 gate；记录保护覆盖与旁路，避免把环境坏掉计为安全成功。
